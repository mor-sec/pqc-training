Post-quantum cryptography, in three models

How a quantum computer breaks today's encryption, and what replaces it

Almost every secure connection starts with RSA or elliptic-curve maths. A large, error-corrected quantum computer solves both. Post-quantum cryptography (PQC) swaps them for problems that quantum computers don't speed up. The models below show the break, why it matters before the machine exists, and the fix.

Shor's algorithm finds a rhythm, and the rhythm gives up the key

RSA is safe as long as nobody can split a large number N into its two prime factors. Shor's algorithm avoids searching for them. Pick a base a, and the sequence ax mod N repeats with some period r. Once r is known, one gcd calculation produces the factors.

The model wraps each value around a ring and stacks the steps upward. Gold points mark each return to 1.

Computer

A classical computer walks the helix one step at a time. For a 2048-bit key the period is a number about 600 digits long.

The same method breaks elliptic-curve keys, and needs a smaller machine to do it.

The attack starts years before the machine exists

Encrypted traffic can be copied today and stored. When a machine that runs Shor's algorithm arrives, the archive opens. Whatever was recorded before you migrated, and still matters on that day, is exposed.

Each column is one year of recorded traffic. Michele Mosca's rule of thumb: if X + Y is greater than Z, you are already late.

Signatures are a different case. Forging one needs the machine to exist at that moment, so key exchange is being migrated first.

The fix hides the key in a noisy lattice

The main replacements rest on a different problem. Given a point near a lattice, find the lattice point closest to it. There is no rhythm for Shor's method to find, and no known quantum algorithm does much better than a classical one.

Here the message is a lattice point and the sender adds noise to it. With the private basis (short, nearly square arrows) rounding snaps back to the message. With the public basis (long, skewed arrows over the same lattice) rounding lands on the wrong point. The wire cell shows the region each basis rounds to.

What breaks and what holds

The damage is confined to public-key cryptography, which means key exchange and signatures. Symmetric ciphers and hashes survive, because the best quantum attack on them (Grover's algorithm) only gives a square-root speedup that a longer key absorbs.

How big the machine has to be

These are published designs for a machine that factors RSA-2048, counted in physical qubits. Each one is a paper estimate that assumes hardware nobody has built, and no machine today is close to running these circuits. The requirement has fallen by more than four orders of magnitude in 14 years, mostly through better algorithms and error-correcting codes.

The replacements

NIST finalised the first three standards in August 2024. Two more are still being written. They split into key exchange (KEMs) and signatures, and they deliberately rest on more than one kind of maths in case one of them falls.

  • ML-KEMFIPS 203 · final · key exchangeLattice-based, from CRYSTALS-Kyber. NIST's recommended default is ML-KEM-768.
  • ML-DSAFIPS 204 · final · signaturesLattice-based, from CRYSTALS-Dilithium. The general-purpose signature.
  • SLH-DSAFIPS 205 · final · signaturesHash-based, from SPHINCS+. Relies only on hash functions, at the cost of large signatures.
  • FN-DSAPlanned FIPS 206 · in development · signaturesLattice-based, from Falcon. Much smaller signatures, harder to implement safely.
  • HQCSelected March 2025 · in development · key exchangeCode-based. A backup for ML-KEM that does not depend on lattices.

The deadlines already set

Governments are not waiting for a date for the machine. NIST's transition plan became final on 27 October 2026 and was stricter than its draft: every key size of RSA and elliptic-curve cryptography is on the clock, where the draft covered only the weaker ones.

If you run systems

  1. Find where RSA and elliptic curves are used. Certificates, VPNs, SSH, firmware signing and hard-coded libraries all count.
  2. Sort data by how long it must stay secret. Anything with a long shelf life goes first, because it is already being recorded.
  3. Turn on hybrid key exchange where your TLS and SSH stacks already support it. That closes the record-now gap today.
  4. Budget for bigger keys and signatures. Handshakes, certificate chains and constrained devices feel it first.
  5. Make algorithms swappable in configuration. The standards are still moving, and you will change them again.
